# 3. MVP 범위 및 근거

## 3.1 범위 선정 원칙

1주라는 기간에서 "많이 만드는 것"보다 **문제 상황에 나온 모든 페인 포인트를 최소 1개의 동작하는 기능으로 해결**하는 것을 우선했다. 기준은 세 가지다.

1. **문제 직결성** — 문제 상황 본문에 직접 언급된 고통인가? (중복·누락, 노쇼, 비표준 기록, 전환 수동 집계, 가족 상담, 마감 이탈)
2. **데이터 선행성** — 지금 만들지 않으면 *나중에 소급할 수 없는 데이터*인가? (예: 상담 기록의 구조화 필드, 추천 제품·관심도. 자유 텍스트로 쌓인 과거 기록은 나중에 집계할 수 없다)
3. **대체 가능성** — 실 서비스 연동이 필요하지만 MVP에서는 **인터페이스만 두고 Mock으로 대체**해도 흐름 검증이 가능한가? (SMS, 본인인증, LIMS 연동)

## 3.2 MVP에 포함한 것

| 페인 포인트 | MVP 기능 | 포함 근거 |
|---|---|---|
| 별도 채널로 연락해야 예약 가능 | 결과지 기반 셀프 예약 + 날짜별 잔여 캘린더 | 모든 흐름의 시작점. 이게 없으면 나머지가 의미 없음 |
| 일정 겹침·예약 누락 | DB 레벨 중복 예약 차단, 단일 예약 원장 | 정합성은 나중에 고칠 수 없는 신뢰 문제. 동시성은 애플리케이션 체크만으로는 막을 수 없어 DB 불변식으로 구현 |
| 원하는 시간 마감 시 이탈 | ① 마감 시 대안 시간 제안 ② 대기 신청 + 빈자리 순차 제안·선점 | 이탈은 *전환 이전에 잃는 매출*. 대안 제안은 저비용, 대기는 취소분을 회수하는 유일한 수단 |
| 당일 연락 안 됨(노쇼) | 리마인더(전날·1시간 전) + 참석 확인 + 통화 번호 지정 + 통화 시도/부재 기록 | 노쇼의 원인은 "잊음"과 "모르는 번호라 안 받음"이 대부분 → 리마인드와 번호 사전 고지가 가장 효과적인 저비용 대책. 부재 기록은 노쇼율 측정의 전제 |
| 기록 방식이 제각각 | 구조화된 상담 기록 폼(태그·논의 지표·추천 제품+관심도·후속 조치), 제출 = 완료 | **데이터 선행성** 1순위. 오늘부터 쌓아야 3개월 뒤 분석 가능 |
| 관심 제품·구매 전환 파악 불가, 수동 집계 | 주문 웹훅 수집 + 전환 귀속 로직 + 대시보드 | 상담 조직의 존재 이유(성과)를 증명하는 기능. 수동 집계 제거 |
| 가족 결과 상담 | 계정 ↔ 피검자 분리, 가족 본인 휴대폰 인증을 마쳐야 등록, 키트 접수 정보(이름·생년월일·휴대폰) 대조 후 결과 연결 | 데이터 모델의 근간이라 나중에 바꾸면 비용이 큼 (**처음부터 분리**). 건강정보라 동의 근거가 필수 |

## 3.3 구현하며 범위에 넣은 것과 이유

처음 범위는 위 표(페인 포인트 해결)였다. 만들면서 **그 기능들이 안전하게 돌아가려면 꼭 있어야 하는 것**이 드러났고, 아래 항목을 범위에 넣었다. 기준은 "이게 없으면 위 기능이 악용되거나, 지표가 틀어지거나, 고객이 막다른 길에 서는가"이다.

| 추가한 기능 | 넣은 이유 |
|---|---|
| 회원가입 + **본인 휴대폰 인증**, 휴대폰 1개 = 계정 1개 | 처음엔 이메일 가입만 계획했으나, 이름·생년월일만으로는 **남의 이름으로 가입해 그 사람 키트를 연결**하는 우회가 재현됨. 건강정보를 보여주는 서비스라 본인 확인은 상담의 전제 |
| 키트 연결 시 접수 휴대폰 대조, 실패 메시지 통일·하루 실패 제한 | 위 우회 차단. 키트 코드가 순번 형식이라 추측 대입도 막아야 함 |
| **비밀번호 찾기** | 로그인 잠금(5회)을 넣으면 회복 경로가 반드시 필요. 휴대폰 인증이 이미 있어 추가 비용이 작음 |
| **회원 탈퇴**(값 단위 삭제·익명 보존) | 민감정보 서비스는 삭제 요청을 처리할 경로가 필수. 행을 지우면 예약·전환 통계와 법정 보존 주문이 깨져서, 누구인지·건강 상태를 알 수 있는 값만 지움 |
| 로그인 보안(연속 실패 잠금, 비밀번호 변경 시 다른 기기 로그아웃) | 건강정보 계정은 탈취 피해가 큼. 훔친 토큰으로 비밀번호를 대입해 계정을 빼앗는 경로를 재현 후 차단 |
| 상담사 계정 발급·비활성화(관리자) | "상담사는 가입 불가" 원칙을 지키려면 발급 경로가 필요. 퇴사·휴직 처리 시 예정 상담·대기 제안을 함께 정리 |
| 문자 링크로 **로그인 없이 참석 응답** | 가족 번호로 리마인더를 받으면 로그인할 수 없어 참석 확인을 못 함. 참석 확인은 노쇼 대책의 핵심 신호 |
| 상담 기록 **수정 기간·사유·이력** | 고객에게 공유된 기록이 소리 없이 바뀌면 신뢰 문제. 수정을 막지 않되 근거를 남김 |
| **처리 누락 경고**(지난 상담 미처리) | 기록·부재 처리가 빠지면 고객은 요약을 못 받고, 전환·노쇼 지표가 '예정'으로 잘못 집계됨 |
| 대시보드 **단계별 이탈 흐름**, 참석 확인 효과 | 핵심 문제 정의("단계마다 샌다")를 숫자로 확인하는 화면 |
| 공개 데모 배포 준비(단일 컨테이너, 데모 계정 보호) | 평가자가 설치 없이 확인. 공개 주소에서 한 사람이 데모 계정을 바꿔 다른 시연을 깨지 않도록 보호 |

## 3.4 MVP에서 제외한 것과 이유

| 제외 항목 | 이유 | 대체/확장 경로 |
|---|---|---|
| 기존 알로스타 계정 SSO | 사내 인증 시스템 스펙 미공개 | 자체 회원가입으로 대체. `users` 테이블은 SSO 연동 시 외부 ID 컬럼만 추가 |
| PASS/통신사 실명 본인확인 | 본인확인기관 계약 필요 | 휴대폰 인증번호(본인·가족) + 키트 접수 정보(이름·생년월일·휴대폰) 대조로 대체 |
| 실제 SMS/알림톡 발송, 발송 실패 자동 재시도 | 외부 계약·발신번호 등록 필요 | `SmsSender` 인터페이스 + 콘솔 Mock, 실패는 `FAILED`로 기록. 구현체 교체와 재시도 주기만 추가 |
| 휴대폰 번호·이름 변경 | 본인 확인 흐름이 하나 더 필요(새 번호 인증 + 기존 가족·예약 연락처 정리), 1주 범위 초과 | 가입용 휴대폰 인증 로직 재사용 |
| 결과지·기록 열람 기록(감사 로그) | 운영 전환 시점의 요구 | 열람 API에 이벤트 적재만 추가하면 됨(접근 지점이 라우터 몇 곳으로 모여 있음) |
| LIMS(분석 시스템) 결과 연동 | 내부 시스템 스펙 미공개 | 시드 결과지 + 키트 코드 연결 API |
| 결제(유료 상담) | 현재 무료 상담으로 가정 | 예약에 `payment_id` 추가로 확장 |
| 통화 녹음·STT 자동 기록 | 법적 고지·인프라 필요, 1주 범위 초과 | 구조화 기록 스키마가 이미 있어 STT 결과를 초안으로 채우는 방식으로 확장 |
| 반복 노쇼 고객 제재 | 부재 데이터가 먼저 쌓여야 정책 설계 가능 | `NO_SHOW` 이력 집계로 정책화 |
| 화상 상담 | 현행 전화 상담 유지 가정 | `Booking.channel` 컬럼 추가 |
| 다중 인스턴스 스케줄러 | MVP는 단일 인스턴스 | 설계 문서 §4.10 참고 |

## 3.5 MVP 성공 기준 (도입 후 측정)

| 지표 | 정의 | 기대 방향 |
|---|---|---|
| 중복 예약 건수 | 같은 슬롯 활성 예약 2건 이상 | 0건 (구조적으로 불가능) |
| 부재율 | 부재 / (완료 + 부재) | 리마인더·참석 확인 도입 전 대비 감소 |
| 참석 확인율 | 참석 확인 예약 / 비취소 예약 | 높을수록 노쇼 예측력 ↑ |
| 대기 → 예약 회수율 | 예약 전환 대기 / 전체 대기 | 기존 0% (대기 수단 없음) → 양수 |
| 기록 제출률 | 기록 제출 / 완료 상담 | 100% (제출이 곧 완료 처리이므로) |
| 상담 전환율 | 완료 상담 중 30일 내 추천 제품 구매 비율 | 수동 집계 → 자동 집계, 상담사·관심사별 개선 포인트 도출 |
